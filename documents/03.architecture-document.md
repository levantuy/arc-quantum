### 1.2 High-level Data Flow
1. **User Action** (Bridge/Swap/Send) → Next.js frontend
2. **Validation & Display** → Frontend validates inputs, shows TX details
3. **User Signs** → MetaMask/Wallet signs transaction
4. **Relay TX** → (Optional) API route validates & relays to Arc Network
5. **Transaction Mined** → Arc Network processes
6. **Record History** → API route stores TX record in PostgreSQL
7. **UI Update** → Real-time feedback to user via polling or events

### 2.2 Architecture Layers Explained

#### **Frontend Layer** (Next.js)
- **Why Next.js**: 
  - Full-stack capability on single Vercel deployment
  - App Router (modern, nested layouts)
  - Server Components reduce JS bundle
  - API Routes for backend logic
  - Environment variable management built-in
  - Zero-config deployment on Vercel
  
- **Alternative considered & rejected**:
  - React SPA + separate backend: Extra complexity, two deployments
  - Vue/Svelte: Smaller ecosystem for DeFi libraries

#### **Blockchain Integration** (wagmi + ethers.js)
- **Why Direct Frontend TX**:
  - User retains full control (signs locally)
  - No private key touches server (maximum security)
  - Lower latency (no relay hop)
  - Arc AppKit recommends frontend-centric approach
  
- **Optional Backend Validation**:
  - API Route can validate TX before user signs
  - Helpful for UX (catch errors early)
  - Not for custody (user still signs & sends)

- **Alternative considered & rejected**:
  - Backend-relayed TX: Requires key custody, security risk
  - Custom Web3 library: wagmi is battle-tested, larger team adoption

#### **Backend Layer** (Vercel Functions + PostgreSQL)
- **Why Vercel Functions**:
  - Scales with zero configuration
  - Same code runs on laptop & production
  - Cost-effective for small traffic
  - No DevOps overhead (critical for small team)
  
- **Why PostgreSQL**:
  - Transactional integrity for TX records
  - ACID guarantees important for financial data
  - Vercel Postgres integrated, managed backups
  
- **Why Prisma**:
  - Type-safe queries (catches errors at build time)
  - Auto schema migrations
  - Great DX for rapid iteration

#### **State Management** (Zustand)
- **Why Zustand**:
  - Minimal boilerplate vs Redux
  - Small bundle size (~2KB)
  - Good for wallet state, TX status tracking
  - Learning curve minimal for small team
  
- **Stores to create**:
  - `walletStore`: Connected account, balance, network
  - `txStore`: Pending TX, history, status
  - `uiStore`: Modal state, notifications, theme

### 3.2 Backend (API Routes) Architecture

**Key API Routes**:

#### **TX Flow**
- `POST /api/tx/validate` — Validate TX before user signs
  - Input: TX params (from, to, amount, chain)
  - Output: Estimated gas, warnings, or errors
  - No TX broadcast yet
  
- `POST /api/tx/confirm` — Record completed TX in database
  - Input: Signed TX hash, TX params
  - Verify signature matches TX
  - Store in PostgreSQL for history
  - Return confirmation details

#### **History**
- `GET /api/history/list?limit=20&offset=0` — Fetch TX history
  - Query database for user's TXs
  - Return formatted list with status

#### **Auth (Admin)**
- `GET /api/auth/nonce?address=0x...` — Challenge for signing
  - Generate random nonce
  - Store in session/cache
  
- `POST /api/auth/verify` — Verify signed message
  - Recover address from signature
  - Check against whitelist (admin addresses)
  - Set HTTP-only session cookie
  
- `POST /api/auth/logout` — Clear session

#### **Balance**
- `GET /api/balance/unified?address=0x...` — Aggregate balances
  - Query Arc RPC for token balances on all chains
  - Sum & return unified view

#### **Admin Config**
- `POST /api/admin/tokens` — Add/update supported tokens
  - Auth required (admin only)
  - Update PostgreSQL token config
  
- `POST /api/admin/bridge-config` — Update bridge parameters
  - Auth required
  - Update bridge limits, fees, etc.

### 3.3 Database Schema (PostgreSQL)

```sql
-- Users table
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  wallet_address VARCHAR(42) UNIQUE NOT NULL,
  is_admin BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Transaction history
CREATE TABLE transactions (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT REFERENCES users(id),
  tx_hash VARCHAR(66) UNIQUE,
  tx_type VARCHAR(50), -- 'bridge', 'swap', 'send'
  chain_from VARCHAR(50),
  chain_to VARCHAR(50),
  token_from VARCHAR(42),
  token_to VARCHAR(42),
  amount_in DECIMAL(38, 18),
  amount_out DECIMAL(38, 18),
  status VARCHAR(20), -- 'pending', 'success', 'failed'
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  INDEX idx_user_tx (user_id, created_at DESC),
  INDEX idx_tx_hash (tx_hash)
);

-- Supported tokens config
CREATE TABLE tokens (
  id BIGSERIAL PRIMARY KEY,
  symbol VARCHAR(10),
  contract_address VARCHAR(42),
  chain VARCHAR(50),
  decimals INT,
  logo_url TEXT,
  is_active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(symbol, chain),
  INDEX idx_chain (chain)
);

-- Bridge config
CREATE TABLE bridge_config (
  id BIGSERIAL PRIMARY KEY,
  chain_from VARCHAR(50),
  chain_to VARCHAR(50),
  is_active BOOLEAN DEFAULT TRUE,
  min_amount DECIMAL(38, 18),
  max_amount DECIMAL(38, 18),
  fee_percentage DECIMAL(5, 2),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(chain_from, chain_to)
);

-- Admin audit log
CREATE TABLE audit_logs (
  id BIGSERIAL PRIMARY KEY,
  admin_id BIGINT REFERENCES users(id),
  action VARCHAR(100),
  details JSONB,
  created_at TIMESTAMP DEFAULT NOW()
);
```

## 4. Implementation Patterns

### 4.1 TX Submission Flow

```typescript
// 1. User submits form
const handleSubmit = async (formData: TxParams) => {
  // 2. Frontend validates
  if (!isValidAddress(formData.to)) {
    setError("Invalid address");
    return;
  }
  
  // 3. Call API to validate (optional but recommended)
  const validation = await fetch("/api/tx/validate", {
    method: "POST",
    body: JSON.stringify(formData)
  });
  
  if (!validation.ok) {
    setError(validation.data.error);
    return;
  }
  
  // 4. Show preview to user
  setPreview(validation.data);
  
  // 5. User signs in wallet (off-chain)
  const txData = buildTxData(formData);
  const tx = await account.sendTransaction(txData);
  
  // 6. API records TX in database
  await fetch("/api/tx/confirm", {
    method: "POST",
    body: JSON.stringify({
      txHash: tx.hash,
      ...formData
    })
  });
  
  // 7. Poll for TX status
  pollTxStatus(tx.hash);
};
```

### 4.2 Error Handling Strategy

**Frontend Errors** (UX-friendly):
- Form validation errors → Show inline feedback
- Network errors → Retry with exponential backoff
- User rejects signing → Graceful cancel message

**Backend Errors** (API):
- 400 Bad Request → Invalid params, send back validation errors
- 401 Unauthorized → Admin endpoints require valid session
- 500 Server Error → Log to error tracking, show generic message to user

**Blockchain Errors**:
- Insufficient balance → Detect early in TX validation
- Gas limit too low → Estimate + buffer in preview
- Contract revert → Catch via eth_call simulation, display reason

### 4.3 Security Patterns

**Private Key Management**:
- ✅ User manages via wallet (MetaMask, etc.) — NO keys touch server
- ✅ Frontend signs TX locally
- ✅ Backend never sees private keys

**TX Verification**:
- ✅ Backend verifies signature matches TX params before recording
- ✅ Check `from` address belongs to authenticated user
- ✅ Validate `to` address against whitelist (for bridge/swap)

**Admin Panel**:
- ✅ Sign-in via wallet signature (not password)
- ✅ HTTP-only session cookies (no JWT in localStorage)
- ✅ Audit logs for all admin actions
- ✅ Rate-limiting on sensitive endpoints

**Data Integrity**:
- ✅ TX records linked to user_id (prevent tampering)
- ✅ Immutable TX hash as unique identifier
- ✅ Timestamps & audit trail for compliance

## 7. Scalability Considerations

### 7.1 Current Capacity (MVP)
- **Users**: Up to ~10k active users on Vercel free tier
- **TX/day**: ~100k transactions (PostgreSQL can handle)
- **Cost**: ~$0-50/month with Vercel + Postgres

### 7.2 When to Scale

| Bottleneck | Solution |
|------------|----------|
| RPC calls slow | Add caching (Redis) or use Arc Node operators |
| Database queries slow | Add read replicas, optimize indexes |
| Function execution time | Offload to background jobs (scheduled functions) |
| Storage large | Archive old TXs to cold storage |

### 7.3 Architecture Adjustments for Scale

**Phase 1 (Current)**: Single Vercel deployment + Vercel Postgres
**Phase 2**: Add Redis for caching + scheduled background jobs
**Phase 3**: Separate admin backend + separate TX indexer service

## 8. Risks & Mitigation

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|-----------|
| **Private key leaked** | Low | Critical | User wallets are responsible; server never stores keys |
| **DB breach** | Low | High | Encrypt sensitive fields, limit data retention, use Vercel managed DB |
| **TX front-running** | Medium | Medium | No centralized ordering; Arc Network MEV-resistant (if applicable) |
| **RPC endpoint down** | Low | Medium | Fallback RPC URLs, health checks |
| **Vercel outage** | Low | High | Monitor uptime, no single point of failure for chain |
| **Admin credentials compromised** | Low | High | Require multi-sig for sensitive operations, audit logs |
| **Slow Arc RPC** | Medium | Medium | Cache results, batch requests, use Arc node operators |
| **TX replay attacks** | Low | High | Include chain ID + nonce in TX, use EIP-712 typed signing |

## 12. Architecture Decision Records (ADRs)

### ADR-001: Why Next.js over separate React SPA + Node backend
**Decision**: Use Next.js App Router for full-stack development
**Rationale**: 
- Single codebase, single deployment on Vercel
- Reduced ops overhead for 2-3 person team
- App Router + Server Components reduce JS bundle
**Trade-offs**: Less flexibility in backend choice, tightly coupled to Vercel
**Alternative**: Vite + Express would give more control but add complexity

### ADR-002: Why direct frontend TX signing over backend relay
**Decision**: User signs TX in wallet, frontend broadcasts directly
**Rationale**:
- Maximum security (no private keys on server)
- Lower latency
- Aligns with Arc AppKit recommendations
**Trade-offs**: Cannot do on-chain ordering; server cannot batch TXs
**Future**: Optional backend validation before signing for UX

### ADR-003: Why PostgreSQL + Vercel Postgres
**Decision**: PostgreSQL managed by Vercel
**Rationale**:
- ACID guarantees important for financial records
- Vercel integration (same deployment, auto-backups)
- Relational schema clear for TX tracking
**Trade-offs**: Less flexible than NoSQL; requires migrations
**Alternative**: MongoDB would be simpler setup but weaker consistency
